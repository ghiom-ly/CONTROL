# تصميم المرحلة 2 — المتاجر والتقرير اليومي والمراجعة

التاريخ: 2026-11-04 · المشروع: NOURS STORE MONITORING (Laravel 12) · يُبنى فوق المرحلة 1 كما هي.

## 1. الغاية ولماذا

فريق المتابعة في شركة النورس يرسل اليوم تقاريره **نصاً في واتساب** وفق «قالب التقرير اليومي المعتمد» (ملحق أ). هذا يجعل التقارير صعبة المراجعة، لا تُجمع، ولا تُبنى منها إحصائيات.
المرحلة 2 تنقل هذا القالب نفسه إلى النظام: الموظف يعبّئ نفس الأقسام التي يعرفها، والمسؤول يراجع ويعتمد، والأرقام المعتمدة فقط تصبح رسمية.

**النجاح:** موظف يتابع 5–20 متجراً يُنهي تقرير شفته في النظام بجهد لا يزيد عن كتابته في واتساب، والمسؤول يرى أمامه قائمة واضحة بالأكواد التي يجب تحويلها للمتاجر والأكواد العالقة مع المناديب.

## 2. الأهداف

1. إدارة المتاجر (إضافة/تعديل/أرشفة) وإسناد موظف أساسي لكل متجر، وصفحة تفاصيل للمتجر.
2. دورة شفت كاملة: بدء الشفت ← تعبئة التقرير ← الإرسال (= نهاية الشفت).
3. نموذج تقرير بنفس أقسام قالب الشركة + الإضافات المتفق عليها (القسم 4).
4. المراجعة: اعتماد، أو تصحيح المسؤول ثم اعتماد، أو إرجاع للموظف مع سبب؛ مع سجل نسخ كامل.
6. شاشة مجمّعة للأكواد غير المُجاب عليها يعلّم عليها المسؤول التحويل للمتجر أو الحل.
5. عند الاعتماد، داخل Transaction واحدة: تصبح المتابعات رسمية، وتُحدّث ملخصات الشحنات، ويُعاد بناء `store_daily_metrics`.

## 3. خارج النطاق (Non-goals)

- الاستيراد من Excel/PDF و OCR (المرحلة 3).
- سجل الاتصالات التفصيلي لكل مكالمة (متجر/عميل/مندوب) وإدارة المشكلات الكاملة (المرحلة 4). هنا فقط **إنشاء** المشكلة من ملاحظة.
- الرسوم البيانية والتحليلات ومقارنة الفترات (المرحلة 5)، وتقارير PDF (المرحلة 6).
- أي اتصال بمنظومة الشحن الحالية — ممنوع في المشروع كله.

## 4. ما يجب تجنبه (Anti-goals)

- نموذج يجعل الموظف يكتب أكثر مما كان يكتب في واتساب (مثلاً: إلزامه بنتيجة لكل كود).
- تحويل القيم غير المُدخلة إلى صفر — `NULL` يبقى «غير متوفر» (قاعدة المرحلة 1).
- ظهور بيانات تقارير غير معتمدة في أي إحصائية أو في `store_daily_metrics`.
- فقدان أي نسخة سابقة من التقرير عند التصحيح أو الإرجاع.

## 5. ما قرّره صاحب المشروع

| الموضوع | القرار |
|---|---|
| مصدر القالب | قالب الشركة في الملحق أ، بأقسامه الأربعة وبترتيبه |
| المحتوى لكل متجر | عدد الأوردرات (أساسي)، وأكواد بعينها مع نتيجتها (اختياري) |
| الإضافات | قُبل كل ما في التصميم المدموج (`report-merged`): نسبة التسليم النهائية والتحسّن، أكواد ونتائج لكل متجر تُغذّي القسم ③ تلقائياً، لصق أكواد دفعة واحدة مع كشف التكرار، رفع السكرينات، تنبيه تجاوز المحاولتين، تحويل ملاحظة إلى مشكلة، زر «نسخ كنص واتساب» |
| شكل الصفحة | صفحة واحدة بالأقسام بالترتيب (⓪ ثم ① … ④)، المتاجر في بطاقات تُفتح وتُغلق |
| من يضيف المتاجر | المسؤول فقط (`stores.manage`) |
| إسناد المتاجر | لكل متجر موظف أساسي؛ ويستطيع أي موظف إضافة متجر آخر لتقريره عند الحاجة (يُعلَّم «خارج متاجره») |
| الرفض | المسؤول يختار: يصحّح بنفسه ثم يعتمد، أو يُرجع للموظف مع سبب |
| عدد التقارير | تقرير لكل شفت؛ قد يكون للموظف أكثر من شفت في اليوم |
| الشفت | يبدأ عندما يُدخل الموظف بيانات البداية، وينتهي عند إرسال التقرير. لا أسماء شفتات ثابتة |
| الاعتماد | التقرير لا يصبح رسمياً إلا باعتماد المسؤول |
| عدد أوردرات المتجر في اليوم | **مجموع** ما كتبه كل الموظفين في كل التقارير المعتمدة لذلك اليوم — كل موظف يكتب الأوردرات التي اشتغل عليها هو في شفته (نص الحقل في الواجهة يوضّح ذلك) |
| قائمة الأكواد المجمّعة | **ضمن المرحلة 2**: شاشة للمسؤول تجمع كل الأكواد غير المُجاب عليها من التقارير المعتمدة، يعلّم عليها «تم التحويل للمتجر» أو «تم الحل» (القسم 6.7) |

## 6. السلوك المطلوب

### 6.1 المتاجر
- قائمة بحث/فلترة (الاسم، الكود، الحالة، الموظف المسؤول). إضافة/تعديل/أرشفة بصلاحية `stores.manage`؛ العرض بـ `stores.view`.
- الحقول الموجودة في جدول `stores` كافية. `code` يُولّد تلقائياً `STR-00001`، و`normalized_name` عبر `ArabicNormalizer`.
- لا حذف لمتجر له تقارير (القيد موجود)؛ الأرشفة بدلاً منه. اسم مكرر (بعد التطبيع) يُرفض.
- **صفحة المتجر:** بياناته، الموظف المسؤول، أوردراته اليومية من التقارير المعتمدة، الأكواد المفتوحة غير المُجاب عليها، ملاحظات التقارير، ومقارنة بسيطة: مجموع أوردرات آخر 7 أيام مقابل الـ7 السابقة (رقمان + الفرق + النسبة).

### 6.2 دورة الشفت والتقرير
الحالات (موجودة): `draft` ← `pending_review` ← `approved` | `rejected` (ثم يعود الموظف للتعديل ويُعيد الإرسال).

1. **بدء الشفت (القسم ⓪):** الموظف يُدخل «إجمالي الطلبيات المكلّف بها» و«نسبة التسليم الحالية %». يُنشأ تقرير `draft` مع `shift_started_at = now()` و`work_date` = تاريخ بدء الشفت.
   - لا يُسمح للموظف بأكثر من شفت مفتوح (`draft`) في وقت واحد. التقرير `rejected` لا يمنع بدء شفت جديد.
2. **التعبئة:** الحفظ كمسودة متاح في أي وقت (حتى يعود الموظف للصفحة لاحقاً في نفس الشفت).
3. **الإرسال (= نهاية الشفت):** يُطلب «نسبة التسليم النهائية %» ثم `submitted_at = now()` والحالة `pending_review`.

### 6.3 أقسام النموذج

**⓪ بداية الشفت** — إجمالي الطلبيات، نسبة التسليم الحالية، (عند الإرسال) نسبة التسليم النهائية. يعرض النظام التحسّن = النهائية − الحالية.

**① ملخص حركة الأوردرات** — بطاقة لكل متجر:
- إضافة متجر بالبحث بالاسم؛ متاجر الموظف المسندة إليه تظهر أولاً في البحث. متجر غير مسند إليه يُعلَّم `is_outside_assignment`.
- «عدد الأوردرات» لكل متجر (nullable). عدد المتاجر والإجمالي يُحسبان تلقائياً.
- اختياري: أكواد تابعها في هذا المتجر، لكل كود نتيجة من `FollowupResult`. إضافة كود واحد أو لصق عدة أكواد (فصل بالمسافات/الأسطر/الفواصل). كود مكرر داخل التقرير نفسه يُرفض برسالة واضحة.
- كود موجود مسبقاً في جدول `shipments` (أي معتمد) لمتجر **آخر**: يُرفض مع رسالة (لا يُنقل الكود بين المتاجر). كود موجود في تقرير آخر **غير معتمد** لمتجر آخر: تحذير فقط، ويُحسم عند الاعتماد (الثاني يُرفض اعتماده حتى يُصحَّح). *(قرار المنفّذ)*
- **الأكواد في المسودة لا تلمس جدول `shipments`** *(قرار المنفّذ)*: المتابعة تُحفظ بـ `shipment_code` و`store_id` نصاً، و`shipment_id` فارغ؛ الشحنة تُنشأ أو تُربط **عند الاعتماد فقط**. يتطلب ذلك في الـ Migration: `shipment_followups.shipment_id` nullable + عمودا `shipment_code` و`store_id`، واستبدال القيد الفريد بـ unique(`daily_report_id`, `shipment_code`).

**② أوقات المحاولات** — قائمة أوقات (HH:MM) للمحاولات الإجمالية في الشفت؛ العدد يُحسب تلقائياً. الحد المسموح يُقرأ من إعدادات النظام (افتراضي 2). تجاوزه **لا يمنع** الإرسال لكن يطلب سبباً، ويظهر شارة تحذير للمسؤول.

**③ الأكواد غير المُجاب عليها** — قائمتان:
- «لم يرد عليها الزبون (لتحويلها للمتاجر)» = كل أكواد التقرير بنتيجة `customer_no_answer`.
- «لم يرد عليها المندوب / لا تُحل» = كل أكواد التقرير بنتيجة `courier_no_answer`.
- الكود الذي أُعطي هذه النتيجة في القسم ① يظهر هنا تلقائياً (مصدر واحد للبيانات: `shipment_followups`).
- يمكن أيضاً لصق أكواد مباشرة في أي قائمة؛ عندها يختار الموظف «لأي متجر» (المتاجر المضافة في ①)، وتُنشأ متابعة بالنتيجة المقابلة. كود معروف مسبقاً يأخذ متجره تلقائياً.
- رفع سكرينات (صور) للقائمة الثانية. إذا كانت القائمة الثانية غير فارغة بلا أي سكرين: تحذير عند الإرسال (لا يمنع).
- رفع سكرينات «مكالمات الزبائن الذين ردّوا» (تعليمات الشركة) كمرفقات عامة للتقرير.

**④ ملاحظات واستفسارات** — نص حر (`notes`, `inquiries` موجودان). خيار «تحويل إلى مشكلة على متجر»: يختار المتجر ونوع المشكلة (`IssueType`) ويكتب الوصف؛ تُنشأ المشكلة في جدول `issues` **عند اعتماد التقرير** (مفتوحة، مرتبطة بالمتجر والتقرير).

**زر «نسخ كنص واتساب»** — يولّد نص التقرير بصيغة القالب في الملحق أ حرفياً (العناوين نفسها)، ويُنسخ للحافظة. متاح في أي حالة.

### 6.4 المراجعة (صلاحية `reports.review`)
- قائمة «بانتظار المراجعة» مرتبة بالأقدم، مع شارات: تجاوز المحاولات، متاجر خارج الإسناد، قائمة مندوب بلا سكرينات.
- صفحة المراجعة تعرض التقرير كاملاً، وأمام المسؤول:
  1. **اعتماد.**
  2. **تصحيح ثم اعتماد:** يفتح النموذج نفسه للمسؤول؛ قبل الحفظ تُؤخذ نسخة في `report_revisions` (سبب: «تصحيح المسؤول»)، ثم يُعتمد.
  3. **إرجاع للموظف:** سبب إلزامي في `rejection_reason`؛ الحالة `rejected`؛ الموظف يرى السبب، يعدّل، ويعيد الإرسال. عند إعادة الإرسال: نسخة في `report_revisions` و`version + 1`.
- الموظف لا يعدّل تقريراً `pending_review` أو `approved`.
- تعديل تقرير معتمد لاحقاً: فقط بصلاحية `reports.admin_edit`، مع نسخة قبل التعديل وإعادة بناء المقاييس.
- لا أحد يعتمد تقريره بنفسه.

### 6.5 ما يحدث عند الاعتماد (Transaction واحدة)
1. `status = approved`، `approved_by/at`.
2. لكل متابعة في التقرير: إنشاء الشحنة إن لم تكن موجودة (`store_id`, `registered_at = work_date`, `first_report_id`) وربطها، ثم `is_official = true`.
3. لكل شحنة متأثرة: تحديث `last_result`, `customer_status`, `courier_status`, `followups_count`, `last_followup_at`, `last_followup_user_id` من آخر متابعة رسمية، وفق الجدول التالي *(قرار المنفّذ؛ ما لا يُستنتج يبقى NULL ولا يُخمَّن)*:

   | النتيجة | courier_status | customer_status |
   |---|---|---|
   | `courier_no_answer` | `no_answer` | NULL |
   | `customer_no_answer` | `answered` | `no_answer` |
   | `courier_answered_still_delayed` | `answered` | NULL |
   | `courier_promised_delivery` | `answered` | NULL |
   | `delivered_after_followup` | NULL | NULL |
   | `returned_or_not_with_courier` | NULL | NULL |
   | `other_issue` | NULL | NULL |

   وأيضاً `processing_status`: `delivered_after_followup` ← `resolved`؛ `customer_no_answer` و`courier_no_answer` ← `open` (إعادة فتح إن كانت مغلقة)؛ غيرها لا يتغير.
4. إعادة بناء `store_daily_metrics` لكل (متجر، `work_date`) متأثر — من التقارير المعتمدة فقط، وبطريقة قابلة لإعادة التشغيل (حذف ثم إعادة حساب للمفتاح، لا زيادة تراكمية).
5. إنشاء المشكلات المطلوبة من القسم ④.
6. سجل تدقيق (`Auditable` الموجود) + إشعار للموظف بالاعتماد أو الإرجاع.

**إعادة الاعتماد بعد تعديل تقرير معتمد** *(قرار المنفّذ)* — العملية كلها قابلة لإعادة التشغيل:
- المشكلات: كل مشكلة تحفظ رابط الملاحظة التي أنشأتها؛ لا تُنشأ مرة ثانية. ملاحظة حُذفت لا تحذف مشكلتها (قد تكون الإدارة بدأت معالجتها).
- الشحنات: كود حُذف من التقرير ← تُحذف متابعته؛ إن لم يبقَ للشحنة أي متابعة وكان `first_report_id` هو هذا التقرير، تُحذف الشحنة (soft delete). ثم يُعاد حساب ملخصات كل الشحنات المتأثرة والمقاييس للمفاتيح القديمة والجديدة.

### 6.7 شاشة الأكواد المفتوحة (صلاحية `shipments.view`؛ التعليم بـ `shipments.followup` للمسؤول)
- تعرض الشحنات **الرسمية** التي آخر نتيجة لها `customer_no_answer` أو `courier_no_answer` و`processing_status` ليس `resolved`/`closed`.
- تبويبان: «لتحويلها للمتاجر» (الزبون لم يرد) و«عالقة مع المناديب» (المندوب لم يرد)، مجمّعة حسب المتجر، مع: الكود، التاريخ، الموظف، عدد المتابعات، السكرينات.
- فلترة بالمتجر والتاريخ والموظف، ونسخ أكواد متجر كنص (للصقها للمتجر).
- إجراءات: «تم التحويل للمتجر» ← `in_progress`؛ «تم الحل» ← `resolved`؛ مع ملاحظة اختيارية، ومسجّلة في سجل العمليات. يمكن التعليم لعدة أكواد دفعة واحدة.
- الكود يخرج من القائمة عند تعليمه محلولاً، أو تلقائياً عندما تأتيه متابعة معتمدة لاحقة بنتيجة أخرى؛ ويعود إليها إذا جاءته متابعة معتمدة جديدة بنتيجة «لم يرد».
- «الأكواد المفتوحة» في صفحة المتجر هي نفس هذه القائمة مفلترة بالمتجر.

### 6.6 الصلاحيات (موجودة في `Permissions`)
`reports.create` (الموظف: تقاريره فقط — Policy: الوصول لتقرير غيره 403)، `reports.view_all`، `reports.review`، `reports.admin_edit`، `stores.view`، `stores.manage`، `shipments.followup`، `issues.create`.

## 7. القيود التقنية

- المكدس الحالي: Laravel 12، Blade + Tailwind v4 + Alpine.js، RTL، خط محلي، MySQL/MariaDB. نفس قاعدة الفصل: Controller رفيع ← FormRequest ← Policy ← Service داخل Transaction.
- تغييرات المخطط تكون **Migration جديدة إضافية** (لا تعديل لملفات المرحلة 1):
  - `daily_reports`: `shift_started_at` datetime، `start_total_orders` uint nullable، `start_delivery_rate` decimal(5,2) nullable، `end_delivery_rate` decimal(5,2) nullable، `attempt_times` json nullable، `attempts_over_limit_reason` text nullable.
  - `report_stores`: `is_outside_assignment` bool default false.
  - `issues`: ربط اختياري بـ `daily_report_id` إن لم يكن موجوداً، ومعرّف الملاحظة المصدر (لمنع التكرار عند إعادة الاعتماد).
  - `shipment_followups`: كما في القسم 6.3 (`shipment_id` nullable، `shipment_code`، `store_id`، قيد فريد جديد).
  - `store_daily_metrics.shipments_count` = مجموع `report_stores.shipments_count` من التقارير المعتمدة لذلك اليوم؛ NULL إذا كانت كلها NULL.
  - `system_settings`: مفتاح `reports.max_attempts_per_shift` = 2.
- المرفقات: جدول `attachments` (morph) والقرص الخاص `storage/app/private/nours`؛ صور فقط (jpg/png/webp)، حد الحجم من `config/nours.php`؛ تُعرض عبر Route محمي بالصلاحيات.
- اختبارات Feature لكل سلوك أعلاه + تشغيل المجموعة كاملة (المرحلة 1 = 39 اختبار) قبل الإنهاء.
- **ملاحظة بيئة:** جهاز التطوير الحالي فيه PHP 8.5 و Node 22، لكن **لا Composer ولا MySQL ولا `vendor/`**. تشغيل الاختبارات يتطلب تجهيز ذلك أولاً.

## 8. متروك للمنفّذ

تصميم الواجهة التفصيلي ضمن نمط المرحلة 1، أسماء الكلاسات والمسارات، تقسيم الـ Services، طريقة الحفظ (طلب واحد للنموذج أو حفظ تلقائي بـ Alpine)، ترقيم التقارير (الآلية الموجودة).
